# 登录态同步与官网输入中断修复（0.1.14）

## 现场诊断

2026-10-24 香港时间，G3P 在同一 `362fc5b` / 0.1.13 容器内：23:04:45 的购买通过账户检查和结账认证，最终在 23:05:22 因无可用自提门店/时段结束，未提交订单。23:10:35 起的队列及后续三次手动购买在购买前账户读取跳转登录页，恢复流程进入“填写官网密码”约 2.1 秒后报 `BROWSER_LOGIN_INPUT_INTERRUPTED`，尚未加购。没有 541，也没有服务重建。

日志中的统一错误无法区分真实失焦、节点替换、文档导航和识别期错误，不能据此断言密码丢失、Cookie 未保存或 Apple 固定五分钟过期。已有日志足以定位本地缺口，本次不额外触发真实购买。

Linux 普通 Chrome 的连续两次租约对照进一步复现：首任务正常；第二任务创建新页后，若原标签页或另一个窗口仍处于前台，任务页保持隐藏，密码输入在约 2.2–2.7 秒后以同一错误终止。合成复现中尚无字符发送，符合现场“填写密码约两秒失败”的特征；现场缺少详细原因，仍不能把它当作当时唯一已证实的原因。

## 输入保护的边界

隔离 Chrome 复现证明：只读识别阶段恰逢页面跳转、同文档 `history.replaceState`，以及首次聚焦时替换等价密码框，均可能触发旧版的同一句输入中断。识别尚未输入的情况，应在原有超时内重新识别；同文档路由变化不等于文档被替换。

输入前的重新绑定必须重新确认当前任务、可见官方认证页面、唯一字段与原账号。输入开始后的焦点被抢、字段/内容变化、真正换页、认证已提交或验证码提交结果未知，继续保留保护，不盲目重输或重复提交。诊断仅记录固定白名单的阶段和原因，不记录输入内容、长度、页面文本或私有 URL。

首次输入前明确激活当前绑定的任务页，并核对真实文档焦点；只检查 `activeElement` 无法证明后台页已获得浏览器焦点。账号、密码、验证码和远程发送文本共用这个边界，输入过程中不反复抢回焦点。浏览器窗口无需用户手工切换。

## HTTP 与常驻浏览器的同步

HTTP 认证成功会保存原账号的 `auth.json`；常驻 Chrome 持有自己的 Cookie。0.1.13 的部分恢复入口未执行同步，旧的补齐逻辑也不会更新已经存在的同名 Cookie。这是两份会话状态可能分叉的代码缺口，不足以证明现场首次账户跳回登录的服务端原因。

新同步使用账号绑定的私有哈希检查点比较来源和浏览器状态。只在 HTTP 来源已改变、浏览器仍为上次观察值时更新对应商城会话键；浏览器自行更新的值优先保留。首次没有比较基准时只补缺失值。精确按域、路径和名称处理，不清空浏览器，不改设备信任、IDMS 事务或浏览器校验 Cookie。

官网明确退出登录的响应先保存其旋转/删除结果，再恢复；不能让旧导出复活已经删除的会话。Cookie 的 HttpOnly、合法 SameSite、域、路径和过期时间在保存、重载和导入中保留。超时、TLS 失败、未知页面仍不等于退出登录，不触发重新认证。

若官网拒绝了 HTTP 会话但没有下发删除，恢复期间也不把该被拒快照推入原浏览器；原浏览器自身状态交给官网判断。只有通过同账号身份核验的导出/探针对，才能作为新同步基准。

## 验证范围

使用合成账号、拦截网络的 Chrome 页面及独立 Docker profile 验证正常输入、同文档变化、输入前节点替换、真实导航/焦点变化和未知提交保护；以两次独立租约检查常驻浏览器第二次操作。会话同步覆盖来源变更、精确删除、浏览器较新状态、账号隔离及旧数据兼容。真实 Apple 是否继续要求认证及实际下单速度由后续现场日志确认。
