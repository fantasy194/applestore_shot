## 共享执行流程的修改

手动、定时和自动队列继续共用原购买入口和原准备接手，不添加第二套下单逻辑。

1. 实物 SKU 使用相同规范格式比较，例如 `MK2P4CH` 与 `MK2P4CH/A` 等价。数量必须是正整数；重复实物行不合并，其他 SKU、数量变化、缺失 SKU 和畸形数量都停止。
2. Review 只能在当前步骤为 Review（或兼容旧模型未声明步骤）且模型有效时使用。当前在 Fulfillment、PickupContact、Billing 时，空白或遗留 Review 不再抢走实际步骤。
3. 接手优先读取本次响应的实际商品区域。出现明确冲突或无效实物行立即停止；存在一致证据时不增加请求。只有全部区域都缺少实物依据，才在同一 HTTP Session 建立独立读取器，只读获取一次购物袋进行确认。
4. 只读读取器不替换原 Checkout 的模型、动态 action、令牌和当前响应；确认后继续原流程，不重新加购，不重建结账，不重放提交。最终 Review 仍严格核对商品、数量、金额、门店、联系人、时段和支付方式。
5. 记录白名单步骤、依据区域、matched/missing/mismatch/invalid 以及公开 SKU/数量。日志不含原始页面、账号、联系人、Cookie、密码或支付链接。

## 性能收益和边界

本轮最值得消除的应用开销是误拒绝已经保留的活 Checkout：它不但终止首项，还让后续项回到需要认证的常规路径。修复后，符合条件的准备可继续原结账，避免因解析缺失或规范差异而白白丢掉预热成果。已有当前商品依据时没有额外网络请求；缺失时增加一次只读核验，实际冲突仍然停止。

本轮首个官网复核 GET 本身已耗时 4.60 秒；该修复不能承诺发现库存后三秒内下单，也不能把库存探针等同于库存预留。不增加同账号路数、不提高用户重试次数、不跳过最终核对。跨后续门店继续复用失败 Checkout 需要额外隔离选店、联系人和时段状态，尚未作为本次修复实施。

## 验证范围

针对性回归覆盖 SKU 规范化、非当前 Review、当前商品缺失后一次只读购物袋确认、原 Checkout 身份保持，以及真实商品/数量冲突、畸形实物行、重复实物行和缺失购物袋依据的停止路径；保留原自提接手、选店、时段、联系人和结账测试。

本次完整 Worker 回归 1072 项（跳过 4 项），Web Rust 177 项、桌面 Rust 170 项通过；前端类型检查、生产构建和版本页脚检查通过。实际 Web 分发包构建及内置 worker/服务离线 smoke 通过。两份依赖锁只改本项目版本，依赖版本不变。

Linux 首轮 CI 暴露旧验证码子进程 fixture 的固定时间假设：子进程可能在父端公开提示前已经退出。测试改用父端实际公开提示的有界握手，再结束子进程，保留两个提示、一次撤回及提示归属的全部原断言。额外人为延后首个提示处理 0.5 秒，旧 fixture 可复现失败，新 fixture 通过；该项只改测试同步，不改生产认证逻辑。

离线测试可以证明这些模型与控制流分支，不代表本轮真实响应已被重放，也不代表真实订单创建、库存保留或付款成功。发布及部署证据另行核实。
