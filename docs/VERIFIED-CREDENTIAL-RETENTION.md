# 已验证凭据保留与认证归属（0.1.18）

## 本次现场

2026-10-25 香港时间，G3P 的 0.1.17 服务自 09:14 起没有重建。17:15 同一维护任务先完成密码认证（`signin/complete` HTTP 200）和商城交换，随后结账再次认证，第二次 `signin/complete` 在 17:15:30 返回 401。17:25 的后续任务弹出 App 密码提示，直到用户 18:16 输入后继续。新密码记录在 18:16:32 写入，保险库可用且能够读取。

0.1.17 即使知道同一密码刚被官网接受，仍会把后一次 `401 / -20101` 当作应删除密码的证据，同时清除服务缓存并阻止下一任务读取保险库。因此，增加“仅精确密码认证阶段才能拒绝”的判断仍不够；需要同时保留已确认的密码依据。上述日志顺序不证明 Apple 返回第二次 401 的内部原因，也不支持把它归因为用户没有保存或容器重启。

## 凭据规则

- App 输入按账号和密码代次缓存；保存选择和“此前被官网接受”的依据通过私有通道传给后续 worker。新密码重置旧依据，迟到结果不能改变较新的密码。
- 保存仍须有本次实际提交、账号匹配且被官网接受的密码依据。密码受理与完整商城会话分开：明确的 `409 / hsa2` 可以确认密码受理，验证码和商城交换仍须分别完成。
- 已被官网接受的当前密码，或与此前确认保存的保险库记录相同的密码，在后续单次认证拒绝时保留。保留密码不代表本次认证成功；当前购买不能跳过认证或提交核验。
- 从未被接受的新候选密码被明确拒绝时，只清理该候选缓存；若存在另一份已存密码，下一任务仍可正常读取。不会以一个永久的 rejected 标记封锁旧保险库。
- 读取失败报告存储错误，保留原密文和缓存；主动“忘记密码”和移除账号仍由用户明确操作。

保存完成后执行实际读取并在内部比较，确认内容一致才记录保存成功。日志只包含凭据状态、来源、认证阶段及保存/可用布尔值；不记录密码、长度、指纹、Cookie、验证码或原始响应。后续可区分“未保存”“保存成功”“读取失败”“保留已验证密码”及“拒绝新的候选密码”。

## 认证阶段与自动恢复

每次 HTTP 认证开始，以及真正提交密码前，重新绑定本轮提交依据。`signin/complete` 的拒绝与账号发现、挑战初始化、验证码、信任及商城交换失败分别记录；包装异常时保留阶段，不能用上一轮成功输入的标记去解释新一轮尚未提交的请求。

首次、恢复、维护、手动和队列继续共用原执行器。对于官网本次明确拒绝密码认证、但本账号具有已验证密码依据的情况，允许在原认证范围通过原浏览器和当前动态入口恢复一次。已进入 Checkout 时保留同一个 Session、Checkout 和购买目标；不重新加购、不重发旧认证、不重放未知订单。新候选密码未经确认时不扩大这条恢复规则；浏览器实际拒绝后结束本次尝试，不循环登录。

成功的会话核验结束后清理本次认证交互标记，避免随后购物袋读取、网络或模型失败被误报成“需要重新登录”。历史认证失败、验证码要求及真正未知提交仍保留各自边界。

## 验证

使用隔离数据和合成密码复现“第一次认证成功并保存 → 第二次密码认证 401 → 后续任务及重启读取”；覆盖服务内存、真实加密文件、私有 IPC、代次、父子认证租约、不同账号、新候选拒绝与旧记录保留、读取和保存失败。恢复测试检查原 Session / Checkout、唯一浏览器接管及无额外加购或提交。

G3P 更新前后只读核对现有加密记录及 worker 读取能力，不需要导出密码或额外发起真实购买。离线认证响应和本地浏览器 fixture 不证明 Apple 将来永远接受认证；本次修复消除的是应用因后续认证失败丢弃已验证密码、反复要求用户输入的路径。
