# 手动、定时与自动队列的购买流程（0.1.9）

## 对比发现

对比本地 `upstream/main` 的 `d417f41` 与 0.1.8：原项目的购买核心是 `duo_killer.purchase_sku`，结账跳到 `/shop/signIn` 时，`reauthenticate_checkout` 使用当前 `Checkout.session`、官网返回的登录 URL 和原响应继续认证，再进入原结账步骤。

手动和定时单路沿用这条路径。旧队列只有“顺序模式且目标 1 路”使用原账号 Service；队列允许同时执行多个目标时，即使每个目标只设 1 路，也会走隔离子进程。子进程的凭据读取和验证码被硬性拒绝，所以同样的结账认证要求在手动入口可继续，在队列入口会失败。这是可复现的代码语义差异；没有用真实账号重现本次现场错误，不能把它说成每次队列失败的唯一原因。

账号页可读、维护 `healthy` 和 Cookie 存在，都不保证之后结账无需认证。增加预热次数或只取消提示文字，不能修复这个差异。

2026-10-24 18:13（香港时间）只读检查 G3P 的过去 24 小时任务：8 次队列购买失败中，6 次带认证暂停标记；16 个购买任务出现冷却信号，3 次手动购买出现 541。相关失败记录均未提交订单。没有持久化的 `CHECKOUT_REAUTH_REQUIRED` / `PARALLEL_SESSION_REAUTH_REQUIRED` 字面错误码，因此现场证据直接确认的是旧冷却及认证暂停阻塞，子进程认证差异另由源码与离线回归证明。此次检查没有触发登录或购买。

## 统一方式

应用状态和官网认证分开处理：本地冷却、旧“需恢复”记录及子任务拿不到凭据是应用协调问题，不应被包装成用户登录要求。只有官网当前响应要求登录时，才进入自动认证。有效会话先走快速只读核验；官网结账专用认证复用原项目接口及现有 Session / Cookie / 信任信息，无需另起浏览器。购买前确实无法核验会话时，才使用父账号的浏览器恢复。

购买执行器统一处理单次购买、准备模式与并发分派，各入口共享同一重试与 legacy 结账核心。队列只负责目标校验、调度、进程配额、取消和完成确认；购买授权仍来自对应目标及账号配置。

保留子进程隔离，因为旧模块的目录、认证路径和交互处理器属于进程全局变量。不能直接用多个线程同时运行正常 Service，否则会串任务目录、配置和提交标记。

购买前由父账号核验并按需恢复浏览器会话；子路遇到结账专用登录入口时，沿用与手动相同的原 Session 认证流程。父账号串行协调同一账号的认证步骤，已保存凭据通过绑定账号、子任务和请求的私有管道提供，验证码在当前应用任务输入后转回对应子路。凭据不写入业务参数、快照文件或日志。取消、进程退出和认证异常均释放认证占用。

认证成功后直接继续已有 Checkout，不从头加购、不另发一次 checkout，不在失败后偷偷重放购买。完整浏览器登录仍由父账号拥有；子路不竞争同一个浏览器 profile。

## 必须保留的行为

- SKU、数量、门店、时段、联系人和金额仍按当次授权核对。
- 已提交但未确认订单时，立即阻止该账号后续派发；已知订单不能掩盖另一路未知提交。
- 当前官网拒绝或凭据错误保留真实原因，不无限重排同一目标，不永久封锁账号的后续正常任务。
- 重启不重放在途购买；旧认证阻止标记可迁移，未知提交标记必须保留。
- 用户已确认之前失败的任务保持失败；升级不把失败记录重新入队，也不补跑历史购买。
- 测试同时覆盖手动和队列的行为一致性，以及实际父子进程的凭据、验证码、取消和失败边界；离线成功不代表真实 Apple 登录或订单成功。

长期原则记录在 [AGENTS.md](../AGENTS.md)：同一业务行为共用执行流程，速度与自动完成优先，调度差异不改变认证能力，未知订单不重复提交。
