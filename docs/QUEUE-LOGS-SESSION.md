# 执行队列、结构化日志与官网会话恢复

本文说明执行队列、日志和账号会话功能。**2026-10-23 上一轮已更新本机 PWA 和 Windows Web 分发包，恢复原三店监控；本次新增的预热流程选择已有离线验证，发布状态另行记录。**公网手机界面、真实官网窗口传输与离线业务链路分别验收；详见[本轮验收记录](QUEUE-LOGS-SESSION-VERIFICATION.md)。

基础启动、库存代理、通知和自提设置见 [自动监控、并发自提与手机 PWA](MONITOR-PWA.md)。

## 从监控进入执行队列

1. 在“自动监控”为各门店目标选择账号，设置 SKU、每路数量、下单路数和失败重试次数，勾选“有货立即自提抢购”。
2. 确认有货后，该账号 / SKU / 门店的目标进入“执行队列”。界面可以查看等待原因、执行结果，并跳转到对应账号任务和日志。
3. 默认“逐个执行”。需要同时处理多个门店时，选择“固定并发”并设置同时执行任务上限。
4. 改变模式或并发上限前，先暂停队列，等待在途任务与账号协调器结束，再保存并继续。暂停保留排队项，不会中途撤销已提交的官网请求。

人工抢购和定时抢购入口继续保留。这里的持久化 FIFO 用于监控已授权的门店目标；原定时任务到点账号忙或已迟到时，仍按原规则停止，不变成延迟补发。

### 两层并发限制

| 设置 | 含义 |
| --- | --- |
| 逐个执行 | 同时执行一项目标；该目标内部仍按其自己的下单路数配置执行。默认目标路数为 1。 |
| 固定并发 | 同时执行 1–10 项门店目标。某项目标完成后，可以补入下一项，不必等待其他目标全部结束。 |
| 每项目标的下单路数 | 同一家店、相同商品的尝试路数，取值 1–10；每路按所设数量购买，可能产生多笔订单。 |
| 队列总子路名额 | 队列内所有账号共用 10 个名额，目标派发前按其下单路数预留，完成或收尾后释放。 |

例如同时执行上限为 3，三项目标分别需要 3、3、5 路时，第三项会等待名额释放，不会开启 11 个队列子路。“同时执行目标数”和“每项目标路数”不能相乘后当作可突破的全局上限。

顺序模式且目标只有 1 路时，账号协调器复用原账号的正常结账链路，可处理官网要求的重新认证。可能重叠的多目标或多路结账使用隔离子进程、认证和配置快照；账号仍由父协调器占用，子进程不共享可变的旧结账模块状态，也不把临时 Cookie 写回原账号。若并发子路需要重新认证，会明确暂停该账号后续分配，提示完成单路官网恢复。

### FIFO、库存新鲜度与等待

队列按库存确认时间的毫秒值排序，同时间使用递增序号保持稳定顺序。账号正登录、等待验证码、执行人工或定时任务时，目标保留原位置；其他可用账号仍能使用空闲名额。有货授权、账号和库存条件均满足后才派发。

- 同账号 / SKU / 门店的一次补货周期只入队一次。未知、网络错误或队列刷新不会重复入队；官网明确无货后再次有货才建立新周期。
- 超过 10 秒的库存样本、未知状态或官网明确无货使未执行目标保留原任务和 FIFO 位置，等待新的有货确认；撤销授权或移除目标同样只等待恢复，不自动取消。候选池仍限定在入队时冻结的授权门店内。
- 未完成队列最多 500 项，另保留有界的完成历史。满额时本轮不新增，监控下一轮仍有货时再尝试。
- “暂停队列”只停止继续分配；“取消”会撤销未执行项，并向在途目标发送取消信号。已经到达 Apple 的提交不能据此视作已撤销，仍需查询官网结果。

目标自己的失败重试配置继续生效：只有确认尚未提交订单的失败才开始下一轮。某目标已有待付款订单或提交未知时，不再为它开启新一轮。**一个目标成功不会自动取消其他已授权门店目标，队列可能继续产生多笔待付款订单。**未知提交则阻止该账号后续自动分配，其他账号可以继续。

上述逐店行为适用于固定单店配置。账号选择[预选多店模式](PICKUP-PREFERENCES.md)后，同一账号、SKU 和数量的候选店合并成一项替代购买意图，按偏好顺序选择一家，不为每家候选店分别下单；配置的并发路数仍独立生效，默认 1 路。模式切换不会自动重放在途或已提交购买，候选池的未知状态也不会重新武装同一补货周期。

## 派发确认与崩溃恢复

本轮采用现成 Tokio 异步执行和有界通道，再由应用保存订单业务状态。队列记录位于数据目录 `settings/purchase_queue.json`，包含目标、发现时间、序号、分配代次和执行状态；不保存付款二维码或签名付款链接。

派发前先持久化分配，再通过账号协调器下发任务。Python worker 返回开始和完成确认（ACK）；Rust 同时核对账号、任务、队列项与分配代次，旧分配的迟到确认不能覆盖重新等待中的任务。收到已核实的完成结果后才释放相应执行状态；进程退出却没有完成确认时，不把它当作成功。

重启时：

- 尚未派发的目标保留排序，清除旧库存依据，暂停并等待用户继续队列及新的库存确认。监控本身仍需重新启动。
- 已派发或正在执行的目标标为中断，不自动重放；相关账号等待核实官网订单。
- 提交未知不能通过“继续队列”直接清除。先处理该账号的官方订单结果，再按界面状态恢复。

本地持久化能保留意图和执行证据，不能让 Apple 的非幂等提交获得天然的“恰好一次”保证。网络超时、进程崩溃和官网已接收请求之间存在结果不明的窗口，应用因此保留停止和核对状态。

### SDK 研究与选型

[Tokio 官方 channels 教程](https://tokio.rs/tokio/tutorial/channels)介绍了由专用任务管理资源、通过有界 `mpsc` 接收命令及使用 `oneshot` 返回结果的模式；通道容量可提供背压。本项目已有 Tokio 运行时和 worker IPC，沿用这些执行原语可保持账号锁、取消和响应通道的一致性。FIFO 持久化、补货去重及未知提交处理由应用补足，不能归因于内存通道本身。

[Apalis SQLite 官方文档](https://docs.rs/apalis-sqlite/latest/apalis_sqlite/)提供持久化任务存储，并支持重试、调度和失联 worker 恢复。它是可以采用的持久化队列方案；接入本项目仍需把 Apple 的“尚未提交失败”“已经下单”“提交结果未知”分别映射，针对未知提交调整自动重试和恢复策略。本轮选择复用已有 Tokio 执行栈并实现应用层 FIFO / ACK，减少对现有账号和结账流程的迁移；这不构成对 Apalis 安全性或可靠性的否定。

## 结构化运行日志

打开“运行日志”，可按账号、任务、类别和级别筛选，自动刷新、翻页及导出已加载记录；执行队列和会话区域提供带筛选条件的跳转。类别包括库存、代理、队列、认证、购买和普通操作。

日志记录时间、事件、阶段及有界的业务字段，例如 SKU、门店、库存状态、队列序号、分配和完成结果、重试轮数、耗时与 HTTP 状态。库存请求错误仍表示未知，不会在日志中变成无货。

数据保存在 `logs/activity.sqlite`，使用 SQLite WAL；默认保留最近 7 天且最多约 10 万条记录。Rust 事件进入有界写入通道，Python worker 共用结构化存储与字段白名单；日志存储失败会报告诊断问题，不改变结账结果，也不会触发下单重放。

密码、验证码、Cookie、令牌、请求正文、联系人、浏览器帧、付款二维码和付款链接不进入结构化日志。远程窗口输入仅记录操作类型，不记录输入文本或按键内容。该数据库保留普通业务诊断元数据，账号认证材料仍由原账号的私有存储管理。

## 保留原账号的官网恢复

工作台“账号与登录”提供“官网登录恢复（保留账号）”。它使用该账号原有的专用 Chrome / Edge 浏览器资料；541 或认证失败不自动删除账号、不更换浏览器资料，也不通过重复预热循环重放认证。原专用窗口还占用配置锁时，先关闭该窗口再恢复。

恢复浏览器先打开空白页，接入诊断后再访问官网首页和购物袋，从当次首页菜单读取唯一的商城登录链接；沿用官网返回的主机、查询参数和首页来源，不预先打开固定账户登录页。官网登录返回首页时，等待认证、信任请求及商城 Cookie 稳定后，只进行一次账号页核验。菜单缺失、异常或被限制时明确停止，不猜测替代入口。差异分析与离线证据见 [官网恢复与空闲会话刷新](STOREFRONT-SESSION-RECOVERY.md)。

在官网窗口完成登录、验证码和官网展示的信任步骤后，程序等待相关请求稳定，再核实官网返回的实际账号和商城会话。只有账号匹配且会话验证成功，才同步有效的 Apple Cookie；不能把“验证码已接受”“页面打开”或 HTTP 200 单独当作商城登录完成。

商城回调 `/shop/signIn/idms/authx` 返回 541，表示本次商城会话交换被拒绝，不等于验证码错误。当前旧会话的只读诊断曾同时观察到尚未过期的 Cookie 和 541，因此不能据此认定 Cookie 已过期，也不能证明“闲置 30 分钟”是其原因。代码保留原资料和错误阶段，交由官方窗口恢复。

## 手机 PWA 预览和操作登录窗口

在手机 PWA 打开当前账号的进行中任务，有官方浏览器窗口时会出现远程预览。点击画面定位输入框，通过输入框发送文本，并使用按键、滚动控件完成官网交互。页面展开时持续刷新预览；旧帧、断线、账号切换或任务结束时禁用操作并清理暂存输入。

远程操作针对本机为该账号、该任务打开的官网页面，不提供任意地址导航或脚本执行。图像和操作经已登录的 PWA API 转发到私有 loopback broker；Rust 在请求前后检查真实任务仍处于运行或等待输入状态，核对账号和私有注册，且不跟随重定向或通过库存代理转发。

浏览器控制线程独立连接该账号的浏览器，即使原登录流程短暂等待，也可继续预览；它只传递内存中的截图和有时效的输入命令。私有注册文件 `browser-remote.json` 不包含截图或输入，窗口结束时移除。公共接口不返回 CDP 端口或控制令牌；截图、API 和输入不进入 Service Worker 缓存。

## 空闲预热与流程选择

工作台“空闲预热”默认开启。每个账号连续 10 分钟没有实际执行下单操作且空闲后，运行所选预热流程。计时从服务启动、重新启用、切换预热流程、最近一次手动/定时/监控下单结束、最近一次预热结束中较晚的时刻计算。未来定时和未派发排队任务不阻止预热，普通查询仅在运行中占用账号，不重置下单空闲计时。间隔固定 10 分钟，旧 30 分钟设置自动迁移；旧配置缺少流程字段时默认使用登录预热。

在工作台“空闲预热”的“预热流程”选择框中设置：

| 选项 | 设置值 | 行为 |
| --- | --- | --- |
| 预热登录（不加购） | `login`，默认 | 用原账号浏览器读取首页、购物袋和账户页，核验账号后同步当前商城 Cookie，再准备空袋缓存；不清空已有购物袋、不加购、不推进结账。 |
| 提前准备自提（不下单） | `pickup_prepare` | 先完成同样的浏览器会话刷新和账号核验，再使用已保存的 SKU、数量、自提门店顺序与时段规则复用手动准备链路；可能加购并推进结账，但始终使用 `prepare_only`，不提交订单、不等待人工点击下单、不开启失败购买重试。 |

两种自动空闲预热均先用原账号的专用 Chrome / Edge 刷新会话，结束后关闭本次浏览器；不再因保存的浏览器校验 Cookie 尚未过期就跳过刷新。后台无头方式不弹出窗口，手动登录、手动预热和“官网登录恢复（保留账号）”继续使用可见窗口。

自动预热需要重新认证或官网信任确认时，立即结束并提示人工恢复；即使已保存密码，也不在后台提交密码或验证码。此限制持续覆盖嵌套的自提准备，任务结束或取消后解除，手动操作仍按原规则执行。403 / 429 / 541 仍按现有访问限制和冷却规则处理。日志中的 `browser_mode=headless` 表示该次自动任务采用后台策略，不表示登录已成功；冷却和已知 541 标记会在启动浏览器前阻止重复请求。入口与刷新回归见 [官网恢复与空闲会话刷新](STOREFRONT-SESSION-RECOVERY.md)。

切换流程会重新等待 10 分钟，正在运行的预热仍按派发时的原流程完成。该次任务的商品、数量也在派发时冻结；不会因选择框变化而重标结果、取消真实下单或重新执行购买。界面保留开关、倒计时、暂缓原因和最近结果。已知待付款订单允许预热，提交结果未知则暂缓。

### 自提准备结果与五分钟复核

- **会话已准备，等待库存**：官网明确无货或没有符合规则的可选时段时，保留已推进到门店选择的结算会话，返回 `waiting_stock` / `preparation_stage=fulfillment`，`review_verified=false`、`order_ready=false`。这不表示已到达 Review、已经选好门店时段或可以立即提交。
- **完整准备完成**：只有推进到 Review 并完成现有商品、数量、自提门店、联系人等核对后，才返回 `prepared` / `preparation_stage=review`，`review_verified=true`、`order_ready=true`。这些字段描述最近一次准备结果，不保证库存或令牌持续有效。

两种准备缓存均仅在现有五分钟窗口内、商品数量、自提方式和配置指纹相符时尝试复用。后续实际下单仍重新 GET 官网当前结算页；部分准备必须重新查询门店并按规则选店、选时段，再核对 Review 后才能提交。完整准备也不能跳过官网当前状态与最终复核；缓存过期、配置或商品变化时重新走正常流程。自动预热间隔是 10 分钟，因此不能把它理解为持续维持五分钟内的有效准备。

实际下单优先取消预热并等待账号释放。定时任务仍受原 3 秒迟到预算约束，无法及时释放时明确失败，不延迟补发。若检查后账号刚变忙，预热立即跳过，不排队插入下单后。

需要重新登录时，停止自动维护并等待人工官网恢复。403 / 429 / 541 进入约一小时冷却，普通需要登录的失败记录约半小时冷却；冷却与需要恢复的状态持久化。冷却结束本身不会完成重新认证，成功的账号验证后才恢复正常空闲维护。

本地浏览器启动、CDP 连接、网络或未识别页面错误显示独立安全诊断，不判定账号过期；失败记录至少冷却 5 分钟，下一次自动维护仍受所配置空闲间隔约束。

**保活只是减少长期闲置和发现会话失效的手段，不能保证消除 Apple 风控、541、登录挑战或结账重新认证。**电脑休眠、隧道断开和官网策略变化也可能影响观察与恢复。
