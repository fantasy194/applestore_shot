# 官网恢复与空闲会话刷新

## 已确认的流程差异

2026-10-23 根据当前源码和 Git 历史复核：正常新增账号先由专用浏览器读取官网首页和购物袋，再通过首页的 `globalnav-store-key` 请求 `/cn/shop/bag/flyout`，使用唯一 `signIn` 链接推进商城认证。该链接的主机、查询参数、页面令牌和商城回调由本次官网响应确定。

原“官网登录恢复（保留账号）”直接在 Chrome 启动参数中打开固定 `/shop/account/home`，通过账户页进入另一种登录入口；导航还早于 CDP 网络监听。新增界面的“官网浏览器登录”备用按钮也使用这条恢复路径，和默认新增流程有所不同。

原自动登录预热在导出的 `shld_bt_ck` 仍可发送时跳过浏览器上下文刷新，随后调用允许重新认证的账户检查。因此，定期预热并不能证明浏览器商城上下文已更新，必要时还可能触发账户重新认证。

删除重加同时更换本地账号目录、浏览器资料、Cookie、信任和恢复标记。该现象与上述差异相符，但不能单独证明入口、Cookie 或信任就是 Apple HTTP 541 的全部原因。代码与本地 fixture 也不能解释 Apple 服务端的全部拒绝条件。

## 修复后的官网恢复

1. 保留账号 UUID、保存的配置、浏览器资料和设备信任；Chrome 从 `about:blank` 启动，先接入诊断再导航。
2. 在同一浏览器中访问首页、购物袋、首页，读取当前菜单链接。与默认新增共享公开 key 和唯一登录链接的解析、校验逻辑；保留链接原主机、查询参数及首页 Referer。
3. 只接受 HTTPS 官方商城的 `/shop/signIn`。同一目标重复出现或相对/绝对地址指向完全相同 URL 时合并为一次导航；多个不同目标、无效行、外域、账户/订单专用登录入口或 HTTP 拒绝均停止，不回退到固定登录页。官网已打开的认证挑战保留，等待用户完成。
4. 官网浏览器助手自动填写账号及可用密码，点击继续 / 登录，并处理明确的信任浏览器选择；验证码与其他安全挑战由本人完成。商城登录返回首页后，等待认证/信任请求结束和有效商城 Cookie 稳定至少两秒，至多读取一次账号页；已有有效登录则直接进入此只读核验。输入、账号绑定及证据见 [官网自动填写](BROWSER-LOGIN-AUTOFILL.md)。
5. 继续通过 `account_info(..., reauthenticate=False)` 核对实际 Apple ID。只有账号一致且会话验证成功，才保存 Cookie 并移除 541 / 维护标记。失败不覆盖原会话文件。

此流程只恢复会话，不加购、不结账、不创建订单。541 后不会自动重发商城认证请求。

## 修复后的自动空闲预热

保留下单空闲十分钟、账号锁、下单优先和未知提交暂停规则；0.1.9 起维护失败按空闲周期再次尝试，不再以旧冷却阻止购买。两种预热流程均以 `--headless=new` 启动原账号浏览器，读取首页、购物袋和账号页，执行官网脚本并取得本次浏览器 Cookie；不以本地仍有未过期 `shld_bt_ck` 作为跳过刷新的依据。不需要 `DISPLAY` 或后台远程窗口；手动登录和官网恢复继续保留 GUI 及其预览，Docker 中由原 Xvfb 提供。

账号核验使用只读模式，成功后同步本次浏览器 Cookie。默认“预热登录（不加购）”随后读取空袋缓存；“提前准备自提”随后沿用用户保存的门店、时段、SKU 和数量推进 `prepare_only`，保留原有不提交订单和五分钟复核边界。

空闲维护范围内遇到普通官网登录时，在同一无头浏览器中用可用密码继续，输入使用鼠标和逐字键盘事件，每字随机 100–200 ms。六位验证码通过当前任务输入后继续，等待验证码不消耗自动操作时限；无法识别的挑战报告具体原因。首次官网浏览器登录、手动恢复、购买前恢复与维护共用同一助手，购买前自动恢复采用 120 秒操作时限。

后台完整登录使用官网 UI。自提准备已进入当前 Checkout 后，若官网要求结账认证，允许在原 Session 和本次登录入口继续，不另启完整登录或重建购买；退出认证范围恢复原限制，准备始终不提交订单。每个账号 / 密码步骤在本次浏览器助手中至多提交一次，导航、字段替换、焦点变化或取消会停止剩余输入。

0.1.9 起历史 541 标记和本地冷却不阻止当前任务正常官网恢复；可用密码自动输入，六位验证码通过当前任务提交后继续。缺少/错误密码或其他无法自动处理的挑战保留明确诊断；官网当次 403 / 429 / 541 停止本次尝试，不循环重放认证。成功核验后更新恢复状态，不删除账号资料。

推荐保留默认“预热登录（不加购）”用于日常会话维护。需要提前推进自提时再选择自提准备。刷新可减少本地上下文长期不更新和后台认证产生的额外请求；是否降低真实 Apple 的 541 发生率，需要独立现场观察，不能保证消除风控。

## 购买前自动核验（0.1.9）

购买先使用现有 HTTP 会话只读核验账号，成功直接继续；无法核验时复用空闲维护和手动登录的官方浏览器助手，自动使用保存的凭据并在必要时请求六位验证码。其他任务的 `healthy` 不替代本次核验，但有效会话无需再启动浏览器。核验在购物袋写操作与并发快照之前完成。旧冷却和标记不作为本次购买的入口门闩；当前官网失败不自动重放购买。详见[购买前会话核验](PURCHASE-SESSION-CHECK.md)。

## 验证和证据边界

- `tests/worker/test_storefront_recovery.py`：动态入口和 Referer、异常菜单、官网挑战保留、认证稳定后一次账号核验、错账号与失败保留、监听接入顺序。
- `tests/worker/test_idle_session_refresh.py`：已有浏览器校验 Cookie 仍刷新、失败不推进、自提先同步再准备、嵌套任务拒绝后台认证、取消后恢复作用域，以及手动行为兼容。
- `tests/worker/test_session_maintenance.py`：原冷却、无头策略、预热选择和自提边界；自提离线桩补充了前置浏览器同步，不连接真实服务。
- `scripts/verify-storefront-recovery-fixture.py`：真实 Chrome/CDP 加独立临时资料，全部页面和浏览器 fetch 在本地拦截，禁用外部 DNS 与 Python HTTP。手动恢复场景验证动态入口、一次模拟 authx、两秒稳定窗口和同主机账号核验；维护场景验证旧 Cookie 被本次页面更新后导出且没有登录/authx；541 场景验证单次拒绝后停止并保留资料。

浏览器 fixture 的身份导入为合成核验，且为避免测试弹窗额外强制 Chrome 无头；生产手动恢复逻辑仍按可见窗口策略执行。安全结果写入本地 `artifacts/storefront-recovery-fixture.json`，不含真实账号、Cookie 值或登录链接。

2026-10-23 本机 worker 全套回归通过 651 项（其中 1 项跳过）。同一浏览器 fixture 另在已有 Linux amd64 运行镜像中挂载本次只读 worker 源码运行：非 root 用户、`--network none`、空 `DISPLAY`、原 seccomp 沙箱配置，三种场景全部通过；自动维护的 `--headless=new` 在测试注入其他参数前即已存在。容器只用独立临时浏览器资料，没有挂载用户数据卷。此证据验证 Linux amd64 无显示器运行和本次源码，不代表新分发镜像已构建发布或 ARM64 已复测。

这些检查证明流程与本地状态处理，不代表真实 Apple 登录成功、541 已根治、长期保活有效或已下单付款。没有使用真实账号进行登录验收，也没有重启用户服务或发布本地运行包。


## 0.1.6 可选后台官网登录恢复

空闲预热新增“官网登录恢复（保留账号）”（`preheat_flow=browser_login`），旧配置继续默认“预热登录”。所选恢复流程沿用手动恢复的首页动态登录入口、同一账号浏览器 profile、Cookie 同步和最终身份核验；自动执行保持无头，不附加购物袋预热、不加购、不下单。缺少应用可用凭据、验证码或安全挑战时停止，提示手动恢复。

恢复流程会保留原有冷却；冷却未结束不启动浏览器。冷却结束后的明确恢复流程可以使用带旧 541 标记的原 profile 尝试一次官方恢复，未核验成功前不删除标记；本次再遇 403 / 429 / 541 即结束并重新进入冷却。普通预热仍尊重 541 标记，不通过该变化循环重试认证。

服务 `session_maintain` 无头策略覆盖嵌套自提准备与浏览器上下文获取，`browser_process.launch_browser` 再强制 `--headless=new`，结束、错误及取消都恢复作用域，手动可见窗口不受影响。应用凭据按账号在当前服务运行中跨任务复用，服务重启清空；浏览器直接输入不采集到应用缓存。系统保险库和浏览器资料的持久化边界见 [官网自动填写](BROWSER-LOGIN-AUTOFILL.md)。

用户从其他流程明确切换到官网登录恢复时，可为非运行中的旧“需登录”状态授权一次后台恢复派发，原冷却与 541 标记不变。若本轮仍需要人工处理，则再次暂停；重复保存同一流程不会重新授权或绕过冷却。


## 0.1.7 菜单状态与重复目标

恢复入口过去把菜单中 `signIn` 行数等同于唯一目标数，且仅在本地已有有效 `as_ltn_cn` 时识别 `signOut`。因此，完全相同的登录链接重复出现，或菜单已识别登录但浏览器需要通过账号读取刷新商城 Cookie 时，都会报“首页菜单未提供唯一的登录链接”。

现在新增账号和官网恢复共享目的地选择规则：保留本次菜单 URL 的主机及查询参数，相对地址按当前首页解析；每一行先校验，完全相同的目标再去重。不同目标、混合 `signIn`/`signOut`、外域或非预期路径仍停止，不从页面文本猜测链接，也不构造固定 authx。

菜单仅提供 `signOut` 时，从本次菜单唯一的官方 `/shop/account/home` 链接执行一次只读导航，再等待原有身份核验。此分支不要求先有本地商城 Cookie，允许这次官网读取刷新 Cookie；如果读取跳转认证、出现信任确认或仍没有有效商城 Cookie，就停止并保留资料，不继续自动输入认证。账号信息仍由 `account_info(..., reauthenticate=False)` 核验，成功前不导入或删除恢复标记。

2026-10-24 匿名只读公开官网核对：首页和 flyout 均返回 200，当前公开响应顶层有 `bag`、`buttons`、`linksHeader`、`links`，其中链接类型含 `bag`、`orders`、`yoursaves`、`account` 和 `signIn`。这次匿名响应没有复现用户已登录浏览器的菜单状态，不能据此断言生产错误仅由重复链接导致。离线回归及真实 Chrome 本地 fixture 分别覆盖重复登录目标、已有登录菜单刷新、认证重定向停止以及原恢复/541 边界；不使用真实账号或真实登录请求。

## 0.1.9 自动恢复优先

上文 0.1.6/0.1.7 中“冷却阻止恢复”和“账号页转入认证立即人工处理”是历史行为，0.1.9 的统一自动入口已取代它们。账号菜单转入官网认证时继续同一页面，正常账号/密码/信任步骤自动完成；六位验证码在当前任务中处理。用户手动打开的登录窗口仍可见，后台维护和购买认证按需无头运行。自动化只使用官网当前页面及原账号身份，最终账号核验成功才导入会话。
