# 0.1.27 下单准入与冗余拦截复盘

## 现场原因

2026-11-04 香港时间只读检查 G3P：当前账号的旧手动订单已经取得明确订单号，取消任务的结果为 `cancellation_unknown`；没有发现该账号的购买提交未知结果。当时保留的 MK2P4CH/A × 1 准备处于 Fulfillment，等待选店，尚未完成 Review。用户已取消本次受阻队列项。

“该账号有待核实订单，请查询官网确认后继续队列”来自应用 Rust 队列判断，并非官网拒绝。旧判断要求历史手动订单出现官网已付款、取消或过期证明，才允许后续队列购买；同一条件却不用于手动准备接手。因此已知订单号的旧待付款记录也会阻挡新授权购买，造成手动与自动入口不一致。

取消结果未确认只描述那一笔已知订单的取消状态，不等于不知道有没有创建订单，也不应阻止另一笔明确授权的购买。修复不修改旧订单事实、不重复取消订单，用户已取消的队列项保持取消。

## 统一执行规则

- 新购买不等待历史已知订单付款、取消或过期；匹配的活准备通过原子认领继续原 worker、Session 和 Checkout，随后进入共用购买执行器。部分准备仍完成本次选店、时段和结算，完整 Review 仍可按原页接手规则继续。
- 尚未到执行时间、尚未触发的定时任务不占用即时购买或队列执行资格。定时任务本身保持原计划，到期仍按同账号单路及原迟到规则处理。
- 不同监控门店保留各自的失败重试次数，不再为了把它们归为一次候选购买而要求次数一致。每家店的授权次数不增加，同组已取得订单后停止剩余候选。
- 修改某一监控目标，只影响被移除、撤销或购买规则实际改变的待执行项；其他独立购买组、账号及同组范围未改变的其他门店，已接收的有效有货信号保留。候选门店集合改变时，该购买组仍按原规则等待新授权和库存确认；普通配置保存不重新开启已经完成或取消的购买组。重新确认后采用当前重试次数，修复降低次数后旧排队项仍沿用旧值的问题。
- 官网已经返回订单号、只是支付资料复核失败，与订单提交结果未知分别表达。手动、准备接手与队列都保留本任务实际订单号及失败原因，不把支付待核实说成已付款，也不因为丢失订单号而挡住另一笔购买。
- 前端购买按钮和轻量摘要同步采用这些规则，已有订单号与未来定时不再通过另一套界面条件禁用购买。

## 同轮追加的两处现场缺陷

18:24:23，原准备续期读取到官网明确 `session_expired`，随后当前购物袋 GET 返回 200，应用在初始化前因结算路径检查停止；没有发出结算或订单提交。恢复函数额外要求 `/shop/checkoutx`，正常初始化却直接使用官网动态 action。18:34 的正常维护日志实际对 `/shop/bagx/checkout_now` 发起 POST 并收到 200。修复删除恢复时写死的路径，沿用当前官方购物袋响应、同一 Session 和正常初始化执行器，不加购或重放最终提交。

18:31:48，R643 的 MK2P4CH 库存出现新的有货事件，但没有新增队列项；该店周期记录仍指向 17:46 入队、17:59 被用户单项取消的第 27 项。单项取消不应在自动购买仍获授权时永久屏蔽门店。修复允许明确未派发且无提交证据的单项取消，在随后新的有效“无货→有货”周期创建新任务。连续有货、未知样本和全队列取消不会重新入队。旧第 27 项保持取消，18:31 的过期事件不补跑。

真正无法确认订单是否创建的提交、同账号正在执行的操作、用户取消以及本次商品/数量/门店授权继续按原业务边界处理。它们不依赖历史维护冷却或旧账号状态。失败、取消和已完成的历史不补跑。

审查覆盖 Rust 购买入口、队列派发、定时触发、准备接手、维护调度，以及 Python 的购买重试和结果恢复。维护冷却已只影响空闲维护，不阻止实际购买；匿名库存查询与账号结账准备查询继续独立。
