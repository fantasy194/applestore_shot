# 浏览器上下文连接超时

## 现象与诊断

树莓派添加账号停在“正在获取浏览器上下文”，随后提示关闭占用专用配置的 Chrome。旧实现把 Playwright 的每次完整 CDP 连接限制为 1 秒，在外层重试 30 秒；这个 1 秒包含端口发现、WebSocket 握手、已有页面和浏览器上下文初始化，并非仅 TCP 建连。失败统一显示“配置被占用”，不能据此认定另一个浏览器正在使用资料。

2026-10-23 在 Pi 的临时、全新 Chromium 资料中观察到调试 HTTP 端口约 2–5 秒就绪；端口就绪后的第一次 1 秒连接仍超时，后续较宽预算能够成功。该检查没有读取真实账号资料，也没有访问 Apple。历史版本丢弃了浏览器 stderr，无法仅靠旧的通用报错判断每一次历史失败的完整原因。

## 修复

- 登录、官网登录恢复和远程预览共用 `worker/browser_cdp.py`。先直接探测本机 `/json/version`，就绪后给完整连接最多 15 秒；各次重试共享 60 秒总预算，不重置截止时间。
- 浏览器提前退出、调试端口未就绪、完整连接超时分别返回安全错误码。可见窗口和后台模式都检查任务取消；不向日志暴露底层端点、账号资料或凭据。
- 预览连接失败时返回停止状态和安全提示，拒绝继续发送输入，避免显示为一直等待新画面。
- 保留专用资料、Cookie、沙箱、现有进程所有权及登录流程。不删除锁文件、不强抢用户窗口，也不因连接失败重新创建账号。

## 回归与部署验收

`tests/worker/test_browser_cdp.py` 使用可控时钟覆盖慢连接、剩余预算、端口超时、早退、取消和错误脱敏；既有登录及预览测试继续运行。

容器内执行 `docker compose exec -T app python - < docker/verify_cdp_startup.py`，使用独立临时资料、真实 GUI Chrome/Chromium 和本机 CDP 代理，将 WebSocket 握手延迟 1.6 秒：先复现旧 1 秒连接失败，再验证新连接、预览和鼠标/文本输入，以及重启后多页面与合成 Cookie 保留。除临时 HTTP 页面外的流量被阻止。GHCR 工作流在原生 amd64 与 arm64 构建中都运行此检查，再发布双架构 manifest。

Pi 更新沿用现有 Watchtower 和 `/home/fantasy/applestore_shot/data:/data`。发布完成后应核对容器实际镜像 revision、健康状态、页面版本及数据挂载；不能把推送成功当作自动更新已完成。上述回归证明本机浏览器连接和输入，不代表真实 Apple 登录或下单已经通过。
